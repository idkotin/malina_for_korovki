# SIM7600 / telemetry incident, 2026-07-19 to 2026-07-20

## Confirmed timeline (Asia/Novosibirsk, UTC+7)

- 2026-07-19 about 07:34: the complete SIM7600 USB composite device stopped
  being usable. GPS, AT/event ports, PPP/DNS and every `/dev/ttyUSB*` endpoint
  disappeared together. `host-monitor` itself remained alive and buffered
  telemetry locally.
- The SQLite outbox retained about 42,000 rows. This disproves SQLite writer
  contention as the cause; the durable outbox worked as intended.
- 2026-07-20 10:27: after a physical restart the modem returned. The complete
  local backlog was acknowledged by the server by 11:42:57.
- 11:43-12:47: fresh GPS and telemetry remained healthy with an empty local
  backlog. A later abrupt loss therefore did not occur while replaying the
  local buffer.
- 14:49:32-14:52:44: the production server ran calculated-history replay. At
  about 14:51 the host temporarily disappeared from the website even though
  Raspberry Pi logs showed a fresh GPS fix and HTTP 202 every two seconds. The
  website became current when replay completed. Running `journalctl -f` was
  read-only and did not restore anything; the timing was coincidental.

## What is and is not established

The 07:34 incident was a physical/driver/firmware-level loss of the USB modem,
not stale NMEA parsing, the website, server SQLite or Amnezia routing. Direct
USB power quality, connector vibration and SIM7600 firmware remain the leading
hardware candidates. A mobile operator can drop PPP or UDP, but cannot directly
remove Linux `/dev/ttyUSB*` devices.

The production website still needs the separately prepared current/live pointer
fix. Until that rollout, server replay/backlog processing can make the map look
stale even while new host requests are accepted.

## PPP configuration discovery

The working mobile connection belongs to `lte.service` and runs:

```text
/usr/sbin/pppd call megafon
```

An obsolete `sim7600-ppp.service` used the broken default `provider` profile,
failed before connecting, and restarted every five seconds. It was disabled on
2026-07-20. Its generic `ExecStop=/usr/bin/poff` is dangerous: stopping it at
14:26 sent SIGHUP to the working PPP session, which recovered automatically at
14:26:57. Do not run `poff` or stop that obsolete unit again while production
PPP is active.

## Recovery policy

Two independent recovery paths exist:

1. An authorized SMS `/reboot` command. It accepts one configured phone number
   from the live Raspberry Pi config; the number is not committed to Git.
2. An optional guarded automatic reboot. It is permitted only when both of the
   following are true:
   - no telemetry batch has been acknowledged for at least 900 seconds;
   - a fresh, unfiltered calibrated weight is strictly below -1000 kg for at
     least 30 seconds, which is the production signal that the factory terminal
     is off.

The normal weight field is intentionally invalid below -1000 kg, but
`Weight.raw` preserves that pre-filter value and is the only value used by the
guard. A stale or missing weight can never authorize reboot.

Before an automatic reboot the latch is fsynced to
`./data/auto_reboot_state.json`. A reboot cannot repeat while the outage
continues. The latch clears only after acknowledged telemetry remains fresh for
60 seconds.

The guarded watchdog runs inside `host-monitor`. This is deliberate: if the
process or kernel is frozen, it cannot prove the terminal's current state and
must not reboot based on an old weight sample. That failure mode still requires
manual SMS (when the modem is alive), physical intervention, or a genuinely
independent hardware power controller.

## Thermal diagnostics

The production AT reader now records the SIM7600 internal temperature
(`AT+CPMUTEMP`) and reported module voltage (`AT+CBC`) every 30 seconds in a
`modem health:` log line. This is intentionally done by the existing owner of
the AT serial port; a separate serial probe must not run alongside it.

For a controlled thermal test, preserve the cold baseline first, then warm the
closed enclosure in measured stages while recording both the SIM7600 value and
an independent enclosure probe. Do not change the APN during the same stage:
that would introduce a second variable and make the result ambiguous.

## SIM/UIM lockup observed 2026-08-09

This was a different failure from the earlier complete USB disappearance. The
SIM7600 composite USB device, GNSS and AT ports stayed present, but PPP ended
with `LCP terminated by peer` / `Modem hangup`. The modem then reported
`+CME ERROR: SIM failure`, QMI reported an errored/uninitialized UIM, and packet
service was disconnected even though GSM signal remained visible.

`AT+CFUN=1,1` reset only the SIM7600 and restored the same SIM to READY, LTE
registration and packet service without rebooting the Raspberry Pi. The field
workaround therefore lives in the single production AT-port reader. It is
disabled by default and reacts only when repeated `AT+CPIN?` probes report an
uninterrupted explicit `SIM failure` for the configured confirmation time.
Operator loss, DNS/server failures, `SIM busy`, an absent SIM and missing AT
responses are deliberately not recovery triggers. A cooldown and rolling reset
limit prevent a reset loop.

The SMS poller previously treated every generic `ERROR` or `+CMS ERROR` as full
SMS storage and repeatedly issued the destructive `AT+CMGD=1,4`. It now clears
messages only for an explicit storage-full indication (`+CMS ERROR: 322`,
`SMS FULL`, or `MEMORY FULL`).

## USB port renumbering observed 2026-08-10

This was distinct from the SIM/UIM failure. Between 15:40 and 16:08 local time
the SIM7600 composite device disconnected from USB about twenty times. The
modem eventually remained present and registered on MTS LTE with strong signal,
but its interface `03` returned as `/dev/ttyUSB4` because the persistent `pppd`
process still held the old disconnected tty minor. `pppd call megafon` kept
running and `lte.service` therefore remained `active`, while `/dev/ttyUSB3`,
`ppp0`, the default route and DNS connectivity were absent.

The guarded SIM-failure recovery correctly did not run: the SIM was READY and
there was no explicit `SIM failure`. A controlled release of the serial users
and USB re-enumeration restored the original tty numbering and PPP. Telemetry
buffering preserved the outage data.

The permanent software mitigation is `/dev/simcom-ppp`, a udev alias for USB
vendor/product `1e0e:9001`, interface `03`. The PPP peer must use this alias
instead of a kernel-assigned `ttyUSBN` name. A separate conservative systemd
timer may restart only `lte.service` when it claims to be active, the stable
alias exists and `ppp0` has been absent continuously for two minutes. It never
reboots the Raspberry Pi or resets the modem USB device.

## Full USB enumeration failure observed 2026-08-11

At 10:00:54 local time the SIMCOM disconnected, briefly enumerated again, and
then the kernel repeatedly reported `Cannot enable. Maybe the USB cable is
bad?` followed by `unable to enumerate USB device`. The modem vanished from
`lsusb`, all `ttyUSB` and QMI devices disappeared, and the stable PPP alias was
therefore correctly absent. Raspberry Pi input power diagnostics showed no
active throttling. A cold Raspberry Pi power cycle restored the modem.

The onboard Raspberry Pi 4 USB hub `2109:3431` was then validated with
`uhubctl 2.6.0`: both companion hubs reported `off`, SIMCOM disappeared from
`lsusb`, and it re-enumerated with a new USB device number after power was
restored. The optional `--enable-usb-power-cycle` installer mode enables a
guarded second watchdog stage for this exact failure. It waits five minutes,
refuses to act on another Pi model or when an unexpected USB device is present,
cycles external USB power for ten seconds, and has a 30-minute cooldown. This
is recovery rather than a root-cause fix; cable, connector, modem-board power,
and SIMCOM firmware remain suspects.
